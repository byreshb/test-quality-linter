# TQL011 UnusedTestResult

**Default severity:** WARN

## What it catches

The code under test is called, its return value is thrown away as a bare statement, and that
same call never appears inside an assertion elsewhere in the method:

```java
@Test
void computesTheTotal() {
  invoice.total();          // computed, then discarded
  assertTrue(invoice.isValid());
}
```

This rule needs symbol resolution to know whether a call's declared return type is void, so it
only produces findings for a linter built with a classpath (see
[docs/configuration.md](../configuration.md) once the CLI's `--classpath` flag exists, or
`new Linter(registry, config, classpath)` when using `tql-core` directly); without one,
`RuleContext.symbolsResolved()` is false and the rule reports nothing rather than guess.

To keep the false-positive rate low, only calls whose resolved return type is a primitive, a
primitive wrapper, `String`, `Optional`, `BigDecimal` or `BigInteger` are considered. A fluent
setter that returns its own type, or a mutator such as `List.add` whose boolean result is
conventionally ignored, is not flagged unless the return type happens to be one of the above;
suppress an individual line with `// tql:ignore TQL011` when that is intentional.

## Why it matters

A discarded return value is easy to miss: the statement compiles, the test runs, and the one
piece of output that could have been checked never was. It is a narrower, more targeted case
than [TQL003](TQL003.md) NoAssertion, since the method may well have a real assertion elsewhere
on something unrelated.

## Bad

```java
@Test
void computesTheTotal() {
  Invoice invoice = new Invoice(List.of(new Line(10), new Line(20)));
  invoice.total();
  assertTrue(invoice.isValid());
}
```

## Fixed

```java
@Test
void computesTheTotal() {
  Invoice invoice = new Invoice(List.of(new Line(10), new Line(20)));
  assertEquals(30, invoice.total());
  assertTrue(invoice.isValid());
}
```

## Options

None.
