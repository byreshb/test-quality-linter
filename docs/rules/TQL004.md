# TQL004 AssertsOnStub

**Default severity:** ERROR

## What it catches

An assertion that compares the value a mock returns back to the exact literal the mock was told
to return, so the assertion checks the test's own mock configuration instead of anything the
code under test computed:

```java
when(repository.count()).thenReturn(5);
assertEquals(5, repository.count());   // flagged
```

Recognised stubbing styles: Mockito's `when(...).thenReturn(...)` and
`doReturn(...).when(mock).method(...)`, Mockito-BDD's `given(...).willReturn(...)`, and
EasyMock's `expect(...).andReturn(...)`. Recognised assertion styles: JUnit's `assertEquals` and
`assertSame` (either operand order, with or without a message), AssertJ's `assertThat(x)
.isEqualTo(y)` / `.isSameAs(y)`, and Hamcrest's `assertThat(x, is(y))` / `equalTo(y)`.

A stub set up in `@BeforeEach`, a field initialiser or another helper method is shared by every
test method, matching how fixtures are normally written; a stub set up inside one `@Test` method
is scoped to that method only, so an unrelated test asserting the same call against the same
value is not flagged.

## Why it matters

The point of a mock is to stand in for a collaborator so the test can focus on how the code
under test *uses* it. Asserting that the mock returns what it was told to return proves the
mocking framework works, not the code under test.

## Bad

```java
@Test
void reportsInventoryCount() {
  when(repository.count()).thenReturn(5);
  assertEquals(5, repository.count());
}
```

## Fixed

```java
@Test
void reportsInventoryCount() {
  when(repository.count()).thenReturn(5);
  String report = reportGenerator.summarise(repository);
  assertThat(report).contains("5 items in stock");
}
```

## Options

None.
